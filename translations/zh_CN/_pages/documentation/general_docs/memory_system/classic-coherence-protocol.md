# Classic 内存系统一致性

M5 2.0b4 引入了一个经过大幅重写和精简的缓存
模型，其中包括一个新的一致性协议。（2.0 之前的旧缓存模型
曾被修补到可以与 2.0beta 引入的新[内存
系统]({{ site.baseurl }}/documentation/general_docs/memory_system/)配合工作，但没有
重写以利用新内存系统的特性。）

新一致性协议的关键特性是：它被设计为
可以配合或多或少任意的缓存层次结构（多个缓存、各自位于多个层级）。相比之下，旧协议把共享限制在
单条总线上。

在现实世界中，系统体系结构会对协议所能容纳的缓存
数量或配置有所限制。设计一个既完全
真实、又能高效应对任意配置的协议并不实际。为了让
我们的协议能在（几乎）任意配置上工作，我们
目前牺牲了一点真实性和一点
可配置性。我们的意图是让该协议足以满足研究系统行为中
一致性机制之外其他方面的研究者。专门研究一致性的研究者可能
希望把默认的一致性机制替换为正在研究的具体协议的实现。

该协议是一个 MOESI 探听（snooping）协议。它**不**强制
包含（inclusion）关系；在 CMP 配置中，如果若干个 L1 的总
容量占它们共享的公共 L2 容量相当大的比例，包含关系可能非常低效。

来自上层缓存（更靠近 CPU 的那些）的请求
按预期方式向内存传播：L1 未命中会在
本地 L1/L2 总线上广播，由该总线上的其他 L1 探听，
（如果都没有响应）则由 L2 服务。如果该请求在 L2 中也未命中，
那么经过一段延迟（目前设为等于 L2 命中延迟）后，
L2 会在其面向内存的总线上发出该请求，在那里它可能
被其他 L2 探听，然后被发往 L3 或内存。

遗憾的是，以类似方式把探听请求逐步向上传播回
层次结构，会产生无数几乎无法处理的
竞态条件。真实系统通常也不这样做；一般而言，
你希望在 L2 总线上的单次探听操作就能告诉你
该块在整个 L1/L2 层次结构中的状态。有几种方法可以做到这一点：

1.  只探听 L2，但强制包含关系，使得 L2 也拥有
    你所需要的一切关于 L1 的信息 —— 这个想法我们上面
    已经否定了
2.  在 L2 处为所有 L1 保留一份额外的标签副本，这样就能
    同时探听它们（参见 Compaq Piranha）—— 如果你的层次结构不太深，这是合理的，
    但现在你必须根据上层缓存的数量、大小和
    配置来决定下层缓存中标签的规模，这在配置上
    很麻烦
3.  让 L1 的探听与 L2 并行进行，如果它们都在同一颗芯片上，这并不难
    （我相信 Intel 从
    Pentium Pro 开始就这么做了；不确定 Core2 芯片是否仍然如此，
    也不确定 AMD 是否也这样做，但我猜是的）—— 这同样
    合理，但为这些探听添加显式路径也会
    使配置过程变得非常繁琐

我们通过引入“快速探听（express snoop）”来解决这个两难问题。快速探听是特殊的
探听请求，瞬时且原子地向上传播到层次结构
（很像[内存
系统]({{ site.baseurl }}/documentation/general_docs/memory_system)页面上描述的 atomic 模式访问），即使系统正在以
timing 模式运行也是如此。在功能上，它的行为非常像上面的方案 2 或 3，
但由于探听沿常规总线
互连传播，不会带来额外的配置开销。这会引入
一些时序不准确，但如果我们假设真实硬件中存在用于这些探听（或用于
在下层缓存中维护上层标签的额外副本）的专用路径，
那么差异大概很小。

（更多内容即将推出：缓存如何知道自己的请求已完成？以及
其他有趣的问题……）

注意：截至 2.0b4，该协议仍存在一些缺陷，
特别是当你有多个 L2、且每个 L2 后面挂着多个 L1 时，
但我认为它对任何在 2.0b3 中可用的配置都能工作。
