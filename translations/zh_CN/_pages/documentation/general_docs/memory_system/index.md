# 内存系统（Memory system）

M5 的新内存系统（在第一个 2.0 beta 版本中引入）设计时设定了以下目标：

1.  在 timing 模式下统一时序访问与功能访问。在旧的内存系统中，时序访问不携带数据，只
    计算执行一次操作所需的时间。随后由一次单独的功能访问真正让该操作对系统可见。
    这种方法令人困惑，它让被模拟的组件可能意外地“作弊”，也阻止了内存系统
    返回依赖时序的值，而这对于 execute-in-execute 的 CPU 模型来说是不合理的。
2.  简化内存系统代码 —— 移除大量
    模板代码和重复代码。
3.  让修改更容易，特别是允许使用共享总线之外的其他内存
    互连（interconnect）。

关于在 2.0b4 中引入的新一致性协议（同时伴随着缓存模型的重大重写），详情请参见
[一致性协议](classic-coherence-protocol "wikilink")。

### MemObject

所有连接到内存系统的对象都继承自 `MemObject`。
该类增加了纯虚函数 `getMasterPort(const
std::string &name, PortID idx)` 和 `getSlavePort(const std::string
&name, PortID idx)`，它们返回与给定名称
和索引对应的端口。该接口用于在结构上把各个 MemObject
连接起来。

### 端口

内存系统的下一个重要概念是端口。端口
用于让各个内存对象相互对接。它们总是成对出现，
一个是 MasterPort，一个是 SlavePort，我们把另一个端口
对象称为对端（peer）。使用端口可以让设计更加模块化。有了
端口，就不必为每一类对象之间都创建专门的接口。每个内存对象都必须至少有一个端口才有实际用处。
主模块（例如 CPU）有一个或多个 MasterPort
实例。从模块（例如内存控制器）有一个或多个
SlavePort。互连组件（例如缓存、桥接或总线）
同时拥有 MasterPort 和 SlavePort 实例。

端口对象中的函数分为两类。`send*`
函数由拥有该端口的对象调用。例如，要在内存系统中发送数据包（packet），CPU 会调用
`myPort->sendTimingReq(pkt)`。每个 send 函数都有一个
对应的 recv 函数，在对端端口上被调用。因此上面 `sendTimingReq()` 调用的实现
就相当于在从端口上调用 `peer->recvTimingReq(pkt)`。采用这种方式，我们只
付出一次虚函数调用的代价，却保持了通用端口，可以
连接任意内存系统对象。

主端口可以发送请求并接收响应，而从
端口接收请求并发送响应。由于一致性
协议的要求，从端口也可以发送探听（snoop）请求并接收探听
响应，而主端口具有镜像的接口。

### 连接

在 Python 中，端口是模拟对象的一等属性，与
Params 非常相似。两个对象可以用赋值运算符指定它们的端口
应当连接。与普通的变量或
参数赋值不同，端口连接是对称的：`A.port1 =
B.port2` 与 `B.port2 = A.port1` 含义相同。Python 对象中
也存在主端口与从端口的概念，并且在端口连接时会
进行相应检查。

总线之类可能拥有数量不限的端口的对象
使用“向量端口（vector port）”。对向量端口的赋值会把对端追加到
连接列表，而不是覆盖之前的连接。

在 C++ 中，所有对象实例化之后，内存端口由 python 代码连接在一起。

### Request

Request 对象封装了 CPU 或
I/O 设备发出的原始请求。该请求的参数在整个
事务（transaction）过程中保持不变，因此对于给定请求，Request 对象的字段至多被写入一次。有若干个构造函数和
更新方法，允许在（不同时间或根本不）写入对象的字段子集。通过会校验所读字段数据是否有效的访问方法，
可以读取所有请求字段。

请求对象中的这些字段在真实系统中通常并不为设备
所知，因此通常只应用于统计信息（statistics）或
调试，而不应作为体系结构层面的值。

Request 对象的字段包括：

- 虚拟地址。如果请求是直接在物理地址上发出的
  （例如由 DMA I/O 设备发出），该字段可能无效。
- 物理地址。
- 数据大小。
- 请求被创建的时间。
- 导致该请求的 CPU/线程 ID。如果
  请求不是由 CPU 发出的（例如设备访问或
  缓存回写），该字段可能无效。
- 导致该请求的 PC。如果请求
  不是由 CPU 发出的，该字段同样可能无效。

### Packet

Packet 用于封装内存系统中两个对象之间的一次传输
（例如 L1 与 L2 缓存之间）。这与
Request 不同：一个 Request 会从请求方一路传递到
最终目的地并返回，途中可能由若干个
不同的 Packet 承载。

许多数据包字段通过会校验所读字段数据是否有效的访问方法
来读取。

数据包包含以下内容，它们都通过访问器读取，以确保数据有效：

- 地址。这是用于把
  数据包路由到其目标（如果未显式设置目的地）并在目标处
  处理数据包的地址。它通常源自
  请求对象的物理地址，但在某些情况下也可能源自
  虚拟地址（例如在地址转换完成之前访问完全
  虚拟缓存）。它可能与原始请求地址不同：例如在
  缓存未命中时，数据包地址可能是要取回的块地址，
  而不是请求地址。
- 大小。同样，该大小可能与
  原始请求的大小不同，如缓存未命中场景所示。
- 指向被操作数据的指针。
    - 由 `dataStatic()`、`dataDynamic()` 和 `dataDynamicArray()`
      设置，它们分别控制与数据包关联的数据是否随数据包一起释放，即分别是不释放、用 `delete` 释放，
      以及用 `delete []` 释放。
    - 如果未由上述任一方法设置，则由 `allocate()`
      分配，并在数据包被销毁时释放该数据。（总是可以安全
      调用）。
    - 可以通过调用 `getPtr()` 取得指针
    - `get()` 和 `set()` 可用于操作
      数据包中的数据。get() 方法执行客户机到宿主机的端序转换，
      set 方法执行宿主机到客户机的端序转换。
- 状态，表示 Success、BadAddress、Not Acknowleged 和
  Unknown。
- 与数据包关联的命令属性列表
    - 注意：状态字段中的数据与
      命令属性之间有一些重叠。这主要是为了让数据包在被
      nack 时易于重新初始化，或易于配合 atomic 或
      functional 访问重用。
- 一个 `SenderState` 指针，它是一个虚基类的
  不透明结构，用于保存与数据包关联、但特定于
  发送设备（例如 MSHR）的状态。指向该状态的指针会在
  数据包的响应中返回，以便发送方快速查找处理它所需的
  状态。会从它派生出特定子类来携带特定发送设备的
  状态。
- 一个 `CoherenceState` 指针，它是一个虚基类的
  不透明结构，用于保存与一致性相关的状态。会从它
  派生出特定子类来携带特定一致性协议
  的状态。
- 指向该请求的指针。

### 访问类型 {#access-types}

端口支持三种访问类型。

1.  **Timing** - 时序访问是最详细的访问。它们
    反映我们对真实时序的最佳努力，并包含
    排队延迟和资源竞争的建模。一旦时序
    请求在未来某个时刻被成功发送，发出该请求的设备
    要么会收到响应，要么在请求无法完成时收到 NACK
    （详见下文）。时序访问与 Atomic
    访问不能在内存系统中共存。
2.  **Atomic** - 原子访问比详细访问更快。它们
    用于快进和预热缓存，返回完成该请求的
    近似时间，不包含任何资源竞争或排队延迟。当发出原子访问时，
    函数返回时就会提供响应。原子访问与时序
    访问不能在内存系统中共存。
3.  **Functional** - 与原子访问一样，功能访问是
    瞬时完成的，但与原子访问不同的是，它们可以在
    内存系统中与时序或原子访问共存。功能访问
    用于诸如加载二进制程序、查看/修改
    被模拟系统中的变量，以及允许把远程调试器
    挂载到模拟器上等场景。需要注意的是，当某个
    设备收到功能访问时，如果它包含一个数据包队列，
    就必须在该队列中搜索受该功能访问影响的请求或响应，
    并相应地更新它们。`Packet::intersect()` 和 `fixPacket()` 方法可以
    在这方面提供帮助。

### Packet 分配协议

Packet 对象的分配与释放协议因访问类型而异。
（这里讨论的是底层 C++ 的
`new`/`delete` 问题，与一致性协议无关。）

- *Atomic* 与 *Functional* ：Packet 对象由
  请求方拥有。响应方必须用响应覆盖请求数据包
  （通常使用 `Packet::makeResponse()` 方法）。
  不支持一个请求有多个响应方。由于响应总是在
  `sendAtomic()` 或 `sendFunctional()` 返回之前生成，
  请求方可以静态分配或在栈上分配该 Packet 对象。
- *Timing* ：时序事务由两条单向消息组成，
  一个请求和一个响应。两种情况下，Packet 对象都必须
  由发送方动态分配。释放由接收方负责
  （对于广播一致性数据包，则由目标设备、通常是内存负责）。
  当请求的接收方要生成响应时，它*可以*
  选择复用请求数据包作为其响应，以省去调用
  `delete` 再 `new` 的开销（并享受使用
  `makeResponse()` 的便利）。不过该优化是可选的，请求方
  不能指望在响应中收到同一个 Packet 对象。
  注意，当响应方不是目标设备时（例如缓存到缓存的传输），
  目标设备仍然会删除请求数据包，因此做出响应的
  缓存必须为其响应分配新的 Packet 对象。此外，
  由于目标设备可能在收到请求数据包后立即删除它，
  任何其他希望在广播数据包被投递之后继续引用它的内存设备，
  都必须对该数据包做一份拷贝，因为被投递的数据包
  指针不能指望一直有效。

### 时序流控

时序请求模拟真实的内存系统，因此与功能访问和
原子访问不同，它们的响应不是瞬时的。由于时序
请求不是瞬时的，就需要流控。当通过 `sendTiming()` 发送时序
数据包时，该数据包可能被接受，也可能不被接受，
这通过返回 true 或 false 来表示。如果返回 false，
该对象不应再尝试发送任何数据包，直到收到
`recvRetry()` 调用。此时它应再次尝试调用
`sendTiming()`；不过该数据包可能再次被拒绝。注意：
不需要重发原来的数据包，可以改为发送优先级更高的数据包。
一旦 `sendTiming()` 返回 true，该数据包仍可能
无法到达目的地。对于需要响应的数据包（即 `pkt->needsResponse()` 为 true），
任何内存对象都可以通过把其结果改为 `Nacked` 并
将其送回来源来拒绝确认该数据包。不过，如果它是响应数据包，
就不能这样做。true/false 返回值用于本地
流控，而 nack 用于全局流控。两种情况下，
响应都不能被 nack。

### 响应与探听范围

内存系统中的地址范围由对某个地址范围
敏感的各个设备处理：它们在各自的从端口对象中提供
`getAddrRanges` 的实现。该方法返回它所响应的地址
的 `AddrRangeList`。当这些范围发生变化时
（例如 PCI 配置发生时），设备应在其从端口上调用
`sendRangeChange()`，以便把新范围
传播到整个层次结构。`init()` 期间正是这样做的；
所有内存对象都会调用 `sendRangeChange()`，于是范围更新会接连发生，
直到每个对象的范围都被传播到系统中的所有总线。
