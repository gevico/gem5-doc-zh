# StaticInsts {#staticinsts} #
StaticInst 提供一条二进制指令的所有静态信息和方法。

它包含以下信息/方法：

* 用于说明指令类型的标志（整数、浮点、分支、内存屏障等）
* 指令的 op 类别
* 源寄存器和目标寄存器的数量
* 使用的整数寄存器与 FP 寄存器数量
* 把一条二进制指令译码为 StaticInst 的方法
* 虚函数 execute()，它定义了对某条指令执行的具体体系结构动作（例如读取 r1、r2，把二者相加并存到 r3。）
* 用于处理内存操作开始与完成的虚函数
* 用于把地址计算与内存访问分开执行的虚函数，供把内存操作拆成两个操作的模型使用
* 反汇编该指令并以人类可读格式打印的方法。（例如 addq r1 r2 r3）

它不包含动态信息，例如指令的 PC、源寄存器的值或结果。这使得 StaticInst 与唯一的二进制机器指令之间是一一映射。我们利用这一点，在 hash_map 中缓存二进制指令到 StaticInst 的映射，从而只需译码一次二进制指令，之后直接使用该 StaticInst。

每条指令集架构（ISA）指令都派生自 StaticInst，并实现自己的构造函数、execute() 函数，如果是内存指令，还要实现内存访问函数。关于这些指令集架构指令如何指定，细节见 ISA_description_system。
# DynInst #
DynInst 用于保存指令的动态信息。对于更详细的模型或乱序模型，这是必需的，因为它们可能都需要除 [StaticInsts](#staticinsts) 之外的额外信息才能正确地执行指令。
它存储的动态信息包括：
* 指令的 PC
* 源寄存器和目标寄存器重命名后的寄存器索引
* 预测的下一个 PC
* 指令的结果
* 指令所属的线程号
* 该指令正在其上执行的 CPU
* 该指令是否被清空

此外，DynInst 还提供 ExecContext 接口。当指令集架构指令被执行时，DynInst 作为 ExecContext 被传入，处理指令集架构对 CPU 状态的所有访问。

详细的 CPU 模型可以派生自 DynInst，创建自己的 DynInst 子类，以实现所需的任何额外状态或函数。相关示例见 src/cpu/o3/alpha/dyn_inst.hh。

# ExecContext #
ExecContext 描述了指令集架构（ISA）用于访问 CPU 状态的接口。虽然有一个文件 `src/cpu/exec_context.hh`，但它纯粹是用于文档目的，类并不会从它派生。相反，ExecContext 是一个隐式接口，由指令集架构假定存在。

ExecContext 接口提供以下方法：
* 读写 PC 信息
* 读写整数、浮点和控制寄存器
* 读写内存
* 记录并返回一次内存访问的地址、预取，以及触发系统调用
* 触发某些全系统（full-system）模式功能

ExecContext 接口的实现示例包括：
* SimpleCPU
* DynInst

关于指令集如何实现的更多细节，请参见指令集描述页面。
# ThreadContext #
ThreadContext 是 CPU 之外的一切访问某个线程全部状态的接口。它提供读写外部对象可能需要状态的方法，例如 PC、next PC、整数与 FP 寄存器以及 IPR。它还提供获取重要线程相关类指针的函数，例如 ITB、DTB、System、内核统计信息（statistics）和内存端口。它是一个抽象基类；CPU 必须通过从它派生、或使用模板化的 ProxyThreadContext 类来创建自己的 ThreadContext。
## ProxyThreadContext ##
ProxyThreadContext 类提供了一种无需从 ThreadContext 派生即可实现 ThreadContext 的方式。ThreadContext 是抽象类，因此任何从它派生并使用其接口的东西都要承担虚函数调用的开销。这个类的创建是为了让用户自定义的 Thread 对象可以在任何使用 ThreadContext 的地方使用，而在单独使用它时又不承担虚函数调用的开销。用户自定义对象只需提供与普通 ThreadContext 完全相同的所有函数，ProxyThreadContext 会把所有调用转发给该用户自定义对象。使用 ProxyThreadContext 的示例见 [SimpleThread](http://gem5.org/SimpleThread) 的代码。
## 与 ExecContext 的区别 ##
ThreadContext 与 ExecContext 略有不同。ThreadContext 提供对单个线程状态的访问；ExecContext 提供指令集架构对 CPU 的访问（这意味着在 SMT 系统上它隐式是多线程的）。此外，ThreadState 是精确定义该接口的抽象类；ExecContext 则是更隐式的接口，必须实现它以便指令集架构能访问所需的任何状态。两者用于访问状态的函数调用略有不同。ThreadContext 提供读写寄存器的方法，接收体系结构寄存器索引。ExecContext 提供读写寄存器的方法，接收一个 StaticInst 和一个索引，其中该索引指的是该 [StaticInsts](#staticinsts) 的第 i 个源寄存器或目标寄存器。此外，ExecContext 提供访问内存的读写方法，而 ThreadContext 不提供任何访问内存的方法。
# ThreadState #
ThreadState 类用于保存各个 CPU 模型共用的线程状态，例如线程 ID、线程状态、内核统计信息、内存端口指针，以及已完成指令数的一些统计信息。每个 CPU 模型都可以派生自 ThreadState 并在其基础上扩展，加入被认为合适的线程状态。一个例子是 [SimpleThread](http://gem5.org/SimpleThread)，其中加入了该线程的全部体系结构状态。不过，并非必须（在某些情况下甚至不可行）把线程的全部状态都集中放在派生自 ThreadState 的类中。DetailedCPU 把寄存器值和重命名映射保存在 ThreadState 之外的自己的类中。ThreadState 只是用来提供一种更便利的方式，把部分状态集中放置并在各个 CPU 模型之间共享。

## 索引 —— 寄存器空间相关内容 ##
更完整的讨论见[寄存器索引](#register-indexing)。

下面是对 CPU 模型中扁平化（flattening）与寄存器索引的“走马观花”式介绍。

首先，指令根据其编码（或由于它总是使用某个寄存器等原因）确定自己需要某个寄存器。为便于讨论，假设我们在谈 SPARC，该寄存器是 %g1，并且第二组 globals 处于活动状态。从指令的角度看，未扁平化的寄存器是 %g1，它很可能只用索引 1 表示。

接下来，我们需要把指令视角下的寄存器堆映射到实际的存储位置。可以把它类比为虚拟内存。指令工作在一个类似虚拟地址空间的索引空间中，而它需要被映射到类似物理内存的扁平化空间中。在这里，索引 1 很可能映射到比如 9，其中 0-7 是第一组 globals，8-15 是第二组。

这就是 CPU 开始介入的地方。索引 9 指向指令期望访问的实际寄存器，让这件事发生是 CPU 的职责。在此之前，所有工作都由指令集架构完成，CPU 无从得知；在此之后，所有工作都由 CPU 完成，指令集架构无从得知。

CPU 可以像简单 CPU 那样直接提供寄存器：用一个数组，代表指令读写第 9 个元素。CPU 也可以做些复杂的处理，例如像 O3 那样对扁平化后的索引继续重命名并映射到物理寄存器。

这一切有一个重要性质，用虚拟内存类比就很好理解：扁平化之前索引空间的大小与之后的大小毫无关系。虚拟内存空间可以非常大（大概会有空洞）并映射到较小的物理空间，也可以很小并映射到较大的物理空间，多出来的部分用于其他时刻使用的其他虚拟空间。你必须确保用（扁平化之后的）正确大小来确定表的规模，因为那才是可能选项的空间。

另一个棘手之处在于，我们会向索引中加入偏移，以区分 int、float 和 misc。这些偏移在扁平化之前可能是一种取值，但扁平化之后需要是另一种取值，才能让它们彼此不重叠且不留空洞。这里很容易出错，这也是我不喜欢用偏移来区分不同类型的原因之一。我更希望看到二维索引，其中第二个坐标是寄存器类型。但在今天的世界里，这是你必须留意的事情。

# 寄存器索引 {#register-indexing} #
gem5 中的 CPU 寄存器索引之所以复杂，是因为需要支持多种指令集架构（ISA），而它们的寄存器语义有时差别很大（寄存器窗口、条件码、基于模式的可选寄存器组等）。此外，这种支持是随着新指令集架构的加入逐步演进的，因此较旧的代码可能没有利用较新的特性或术语。
# 寄存器索引的类型 #
CPU 模型内部使用的寄存器索引有三种类型：相对（relative）、统一（unified）和扁平化（flattened）。
## 相对（Relative） ##
相对寄存器索引是机器指令中编码的索引。每一类寄存器（整数、浮点等）都有各自从 0 开始的索引空间。寄存器类别由操作码隐含决定。因此，源寄存器字段中的值 "1" 可能表示整数寄存器 1（例如 "%r1"），也可能表示浮点寄存器 1（例如 "%f1"），取决于指令类型。
## 统一（Unified） ##
虽然相对寄存器索引有利于保持指令编码紧凑，但它们有歧义，因此不便于处理依赖关系之类的事情。为避免这种歧义，译码器会把相对寄存器索引映射到统一寄存器空间，做法是加上各类别专用的偏移，把每个相对索引区间重新安置到唯一的位置。整数寄存器不做改动，仍然从零开始。浮点寄存器索引至少偏移整数寄存器的数量，从而第一个 FP 寄存器（例如 "%f0"）得到的统一索引大于最后一个整数寄存器的索引。类似地，杂项（又称控制）寄存器被映射到 FP 寄存器索引空间之后。
## 扁平化（Flattened） ##
统一寄存器索引对某个执行时刻可作为指令操作数访问的所有寄存器给出了无歧义的描述。遗憾的是，由于某些指令集架构的复杂特性，它们并不总能无歧义地标识指令所引用的实际状态。例如，在带寄存器窗口的指令集架构（尤其是 SPARC）中，某个寄存器标识符（如 "%o0"）在 "save" 或 "restore" 操作之后会引用与之前不同的寄存器。有些指令集架构还有在正常操作中隐藏的寄存器，但在发生中断时（例如 ARM 的模式专用寄存器）或由显式的特权级控制（例如 SPARC 的 "alternate globals"）时被映射到普通寄存器之上。

我们通过维护一个扁平化寄存器空间来解决这个问题，它为每一个唯一的寄存器存储位置提供独立的索引。例如，SPARC 扁平化寄存器空间的整数部分为 globals 和 alternate globals、以及每个可用的寄存器窗口都提供了不同的索引。把统一或相对寄存器索引转换为扁平化寄存器索引的“扁平化”过程因指令集架构而异。在某些指令集架构上，该映射很平凡，而其他则使用表查找来完成转换。

统一寄存器索引与扁平化寄存器索引的生成之间有一个关键区别：前者总能静态完成，而后者常常依赖动态处理器状态。也就是说，从相对索引到统一索引的转换只依赖指令本身提供的上下文（这很方便，因为转换在译码器中完成）。相比之下，映射到扁平化寄存器索引可能依赖处理器状态，例如中断级别或 SPARC 上当前的窗口指针。

## 组合使用各种寄存器索引类型 ##
虽然修改寄存器索引的典型流程是 相对 -> 统一 -> 扁平化，但事实上“相对 vs 统一”与“扁平化 vs 未扁平化”是正交的属性。相对 vs 统一表示该索引是相对于其寄存器类别（整数、FP 或 misc）的基址，还是已经加上了该类别的基址偏移。扁平化 vs 未扁平化表示该索引是否已根据运行时上下文（例如寄存器窗口调整或替代寄存器堆模式）进行了调整。因此，相对扁平化寄存器索引就是已经考虑了运行时上下文、但仍然相对于其类别基址偏移来表示的索引。

无论索引是扁平化还是未扁平化，都使用同一组类别专用偏移来从相对索引生成统一索引。因此这些偏移必须足够大，即使在扁平化地址下也能把各寄存器类别分开。其结果是，未扁平化的统一寄存器空间常常是不连续的。

由此得到的寄存器堆布局以及统一扁平化寄存器堆索引见右侧。虽然图中的索引从 0 到 15，但实际有效索引集合取决于索引类型，对相对索引而言还取决于寄存器类别：

| 相对未扁平化（Relative unflattened） | Int: 0-3; FP: 0-2; Misc: 0-1 |
| 统一未扁平化（Unified unflattened）   | 0-3, 8-10, 14-15             |
| 相对已扁平化（Relative flattened）   | Int: 0-7; FP: 0-5; Misc: 0-1 |
| 统一已扁平化（Unified flattened）     | 0-15                         |

# 注意事项 #
* 虽然 gem5 代码中不幸并不总能清楚说明某个函数期望哪种寄存器索引类型，但函数名中带有寄存器类别的函数（例如 readIntReg()）期望相对寄存器索引，而期望扁平化索引的函数往往在函数名中带有 "flat"。
* 虽然一般情况很复杂，但常见情况可能简单得具有欺骗性。例如，由于整数寄存器从统一寄存器空间的开头开始，整数寄存器的相对索引与统一索引是相同的。此外，在没有（或极少使用）替代整数寄存器的体系结构中，未扁平化与扁平化索引也（几乎总是）相同，这意味着在这种情况下四种寄存器索引类型可以互换使用。这种情况看似是一种简化，却也容易掩盖误用错误寄存器索引类型的缺陷。
* 上述描述旨在说明这些索引类型的典型用法。可能存在并不严格遵循该描述的特例，但我已经厌倦在每个句子里都写“通常”。
* “相对”和“统一”这两个术语是为本文档而造的，因此在代码跟上本页之前，你不太可能在代码中看到它们。
* 这里的讨论只涉及体系结构寄存器。像 O3 这样的乱序 CPU 模型增加了一层复杂性：它把这些体系结构寄存器（使用扁平化寄存器索引）重命名到下层物理寄存器堆。


## 指令集架构与 CPU 的独立性 ##
