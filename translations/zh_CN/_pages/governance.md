gem5 是一个以精英治理（meritocratic）、以共识为基础的社区项目。
任何对项目感兴趣的人都欢迎加入社区、为其设计做贡献并参与决策过程。历史上，gem5 一直在工业界和学术界共同开发。
本文档概述社区参与如何进行，以及个人如何在项目中积累资历。

本文档分为若干章节。
[理念](#philosophy)概述 gem5 社区的核心原则。
[GitHub Issues](#gem5-github-issue-tracker)指引用户前往我们用于 gem5 开发的 GitHub issue 跟踪器。
[角色与职责](#roles-and-responsibilities)定义 gem5 用户的不同类别、贡献者的类型及其职责。
[支持](#support)说明社区如何帮助用户，而[贡献流程](#contribution-process)详述如何做贡献。
最后，[决策流程](#decision-making-process)描述决策是如何做出的。

## 理念 {#philosophy}

gem5 的目标是提供一个工具，推动计算机体系结构领域的state of the art。gem5 可用于（但不限于）计算机体系结构研究、前沿开发、系统级性能分析与设计空间探索、软硬件协同设计，以及底层软件性能分析。gem5 的另一个目标是成为计算机体系结构的通用框架。学术界的通用框架能让其他研究者更容易共享工作负载与模型，并与其他体系结构技术进行比较和对照。

gem5 社区力求在三类用户（学术研究者、工业界研究者和学生，下文详述）的需求之间取得平衡。例如，gem5 力求在加入新特性（对研究者重要）与保持代码库稳定（对学生重要）之间取得平衡。以下列出社区所关注的具体用户需求：

*   以在模拟（simulation）性能与准确性之间取得平衡的方式，有效且高效地仿真现代处理器的行为
*   作为一个易于塑形的基础设施，可以方便地调整以仿真所需行为
*   提供一组保持相对稳定的核心 API 与特性
*   纳入能让公司和研究组轻松跟进最新进展、并持续为项目做贡献的特性

此外，gem5 社区致力于开放、透明与包容。gem5 社区中各种背景的参与者都应感到受欢迎，并受到鼓励去贡献。

## gem5 GitHub issue 跟踪器 {#gem5-github-issue-tracker}

[gem5 GitHub issue 跟踪器](https://github.com/gem5/gem5/issues)列出已知缺陷、功能与改进建议。
希望参与 gem5 工作的人可以浏览这些 issue，并申请指派那些他们认为自己能承担的任务。
鼓励各类用户提出自己的缺陷报告或改进建议。
虽然对 gem5 的贡献可以不经先在 GitHub issue 跟踪器中登记就提交，但它仍然是本项目为后续发布排定优先级、管理工作的主要方式。

## 角色与职责 {#roles-and-responsibilities}

### 用户

用户是对项目有需求的社区成员。他们是社区中最重要的成员，没有他们项目就没有意义。任何人都可以成为用户；没有特殊要求。目前 gem5 用户主要有三类：学术研究者、工业界研究者和学生。个人可以在各类别之间转换，例如研究生去公司实习后再回到学校，或者学生毕业并在工业界就职时。这三类用户描述如下。

#### - 学术研究者

这类用户主要包括把 gem5 用于学术研究的个人。
例如（但不限于）研究生、研究科学家和博士后。这类用户常把 gem5 作为发现和发明新的计算机体系结构机制的工具。学术研究者往往最初是作为[学生](#--students)接触 gem5 的，并随着时间从学生转变为学术研究者。

由于这些用户的目标，他们主要向 gem5 添加新特性。gem5 社区重视鼓励这些用户把工作贡献到 gem5 主线仓库。通过鼓励这些用户提交其研究贡献，gem5 将让其他研究者更容易与其他体系结构技术进行比较和对照（见[理念](#philosophy)一节）。

#### - 工业界研究者

这类用户主要包括在使用 gem5 的公司中工作的个人。这些用户与学术研究者的区别有两点。第一，工业界研究者往往是更大团队的一部分，而不是各自独立地在 gem5 上工作。第二，工业界研究者常常希望把专有信息纳入 gem5 的私有分支。因此，工业界研究者往往会围绕 gem5 构建相当成熟的软件基础设施。对这些用户而言，gem5 特性与基线源码的稳定性很重要。另一个关键考量是模型的保真度，以及它们准确反映真实实现的能力。为了让工业界能够参与，保持许可条款不限制或不过度增加 gem5 与专有 IP 一起使用的负担至关重要。

#### - 学生 {#--students}

这类用户主要包括在课堂环境中使用 gem5 的个人。这些用户通常具备一些计算机体系结构基础，但使用模拟工具的背景很少或没有。此外，这些用户可能在完成其短期目标（例如一学期的课程）后，不会长时间使用 gem5。

项目请求其用户尽可能参与项目和社区。用户的贡献能让项目团队确保满足这些用户的需求。常见的用户贡献包括（但不限于）：

*   为项目做宣传（例如在网站上添加链接、口口相传提高知名度）
*   从新用户的视角向开发者反馈优点与不足
*   提供精神支持（一句“谢谢”很有意义）
*   提供资金支持（软件是开源的，但其开发者要吃饭）

持续参与项目和社区的用户往往会越来越投入。这类用户可能会发现自己成为了贡献者，如下一节所述。

### 贡献者 {#contributors}

贡献者是以具体方式为项目做贡献的社区成员。任何人都可以成为贡献者，贡献可以有很多形式。没有特定的技能要求，也没有选拔流程。

对项目只有一项投入程度的期望：**贡献者在评审过程中必须相互尊重，并共同努力达成妥协**。关于贡献过程的更多内容见[评审补丁](#reviewing-patches)一节。

除了作为用户的行为之外，贡献者还可能做以下一项或多项事情：

*   在邮件列表上回答问题，尤其是新用户提出的“简单”问题（老用户往往最适合支持新用户），或与自己经历相关的问题
*   报告缺陷
*   明确需求
*   提供图形与网页设计
*   编程
*   协助项目基础设施
*   撰写文档
*   修复缺陷
*   添加特性
*   充当大使，帮助推广项目

贡献者主要通过 GitHub 与项目互动。他们通过提交到 GitHub 的补丁把改动提交到项目源码，现有维护者会考虑是否将其纳入项目（见下一节）。在第一次贡献时，开发者邮件列表是寻求帮助最合适的场所。

随着贡献者积累经验、熟悉项目，他们在社区中的形象和对社区的投入都会提升。在某个阶段，他们可能会被提名成为维护者。

### 维护者

维护者是那些通过与社区持续互动、表明自己致力于项目持续开发的社区成员。维护者身份让贡献者能更轻松地继续其项目相关工作，因为这让他们能直接访问项目资源。也就是说，他们可以直接修改项目产出，不过仍须通过 GitHub 提交代码改动。此外，维护者应保有一份持续的贡献记录，包括代码、评审和/或讨论。

维护者对项目的权力并不比贡献者更大。虽然维护者身份表明该成员是社区中被认可、对项目目标与宗旨表现出良好尊重的人，但他们的工作仍会被社区评审。维护者与贡献者的关键区别在于：维护者负有把拉取请求合并到主线的额外职责。此外，维护者应当参与讨论、评审补丁。

任何人都可以成为维护者。唯一的期望是维护者已表现出作为团队一员参与项目的能力。具体请参见[贡献者](#contributors)一节第 2 段。

通常，潜在的维护者需要表明自己理解项目、其目标与策略（见[理念](#philosophy)一节）。他们还需要在一段时间内为项目做出了有价值的贡献。

新维护者可以由任何现有维护者提名。提名之后，将由项目管理委员会（PMC；见下文）投票。维护者提名与投票是少数在项目私有管理列表上进行的活动之一。这是为了让 PMC 成员可以自由表达对提名人的看法而不造成尴尬。投票完成后，会通知提名人结果。无论投票结果如何，提名人都有权要求就其收到的任何反对票给出解释。该解释由 [PMC 主席](#pmc-chair)提供，并将是匿名且建设性的。

提名人可以拒绝被任命为维护者。不过这种情况很少见，因为项目不期望社区成员做出任何特定的时间或资源投入。维护者这一角色背后的意图是让人们更容易为项目做贡献，而不是以任何正式方式把他们绑在项目上。

重要的是要认识到维护者身份是一种特权，而不是权利。该特权必须被赢得，而一旦赢得，在极端情况下可以被 [PMC](#project-management-committee) 撤销。不过在正常情况下，只要维护者持续参与项目，维护者身份就一直存在。

如果某位维护者表现出高于平均水平的贡献，尤其是在项目的战略方向和长期健康方面，他可能被提名成为 PMC 成员。该角色描述如下。

注意：维护者的权威名单保存在一个 GitHub Team 中，由于 GitHub 的限制，该名单不公开可见。网站等处的列表可能已过时。

### 项目管理委员会

项目管理委员会由在开发站点上被标识为 "project owners" 的个人组成。PMC 在维护者之上还有额外的职责。这些职责确保项目顺利运行。PMC 成员应当评审代码贡献、参与战略规划、批准对治理模型的改动，并管理软件的发布与许可方式。

部分 PMC 成员负责 gem5 项目的特定组件。这包括 gem5 源码模块（例如 classic 缓存、O3CPU 模型等）和项目资产（例如网站）。当前组件列表及负责成员见 [MAINTAINERS](https://github.com/gem5/gem5/blob/stable/MAINTAINERS.yaml) 文档。

PMC 成员对社区其他成员没有显著的权力，不过新维护者由 PMC 投票决定。当社区无法达成共识时，也由 PMC 做决定。此外，PMC 可以访问项目的私有邮件列表。该列表用于敏感议题，例如新维护者的投票以及无法公开讨论的法律事务。它从不用于项目管理或规划。

PMC 成员资格由现有 PMC 成员邀请。一次提名会先引发讨论，然后由现有 PMC 成员投票。PMC 成员资格投票需要现有 PMC 成员达成共识批准。新增 PMC 成员需要 PMC 成员一致同意。把某人从 PMC 移除需要 N-1 张赞成票，其中 N 是不包括被投票移除者本人在内的 PMC 成员人数。

### PMC 主席 {#pmc-chair}

PMC 主席由 PMC 成员投票产生，只有一人。某人被任命为主席后，会一直担任该角色，直到他选择退休，或 PMC 以三分之二多数票将其免职。

PMC 主席对 PMC 其他成员没有额外权力：该角色是协调者与促进者。主席还应确保所有治理流程都得到遵守，并在任何项目决策未能达成共识时拥有决定票。

## 贡献流程 {#contribution-process}

任何能够尊重他人的人都可以为项目做贡献，不论其技能如何，因为贡献的方式有很多。例如，贡献者可能在项目邮件列表和 issue 跟踪器上活跃，或者提供补丁。各种贡献方式在另一份文档[提交贡献]({{ site.baseurl }}/contributing)中有更详细的描述。

[GitHub discussions](https://github.com/orgs/gem5/discussions) 或 [GitHub issues](https://github.com/gem5/gem5/issues) 是贡献者在做第一次贡献时寻求帮助最合适的场所。关于 gem5 贡献流程的细节，见 gem5 网站上的[提交贡献]({{ site.baseurl }}/contributing)页面或 [CONTRIBUTING.md](CONTRIBUTING.md)。每个新贡献都应以补丁形式提交到我们的 GitHub 站点。随后其他 gem5 开发者会评审你的补丁，可能要求修改。在补丁获得共识之后（见[决策流程](#decision-making-process)），该补丁就可以提交到 gem5 树中。对贡献者而言，应由维护者批准并为你合并该变更集。如果维护者没有在合理时间内（几天）合并该变更集，请向 gem5-dev 列表发送一封友好的提醒邮件。补丁提交到 gem5 之前，必须至少获得 2 个批准。如果某个补丁没有任何评审，用户应发送后续说明请求评审。

#### 评审补丁 {#reviewing-patches}

贡献流程的重要一环是对其他开发者提交的补丁提供反馈。评审补丁的目的是剔除明显缺陷，并确保 gem5 中的代码质量足够。

鼓励所有用户评审发布在 GitHub 上的贡献。如果你是 gem5 的活跃用户，最好持续关注发布在那里的贡献（通常通过订阅 gem5-dev 邮件列表），这样当你看到可能影响你自己使用 gem5 的贡献时就能发声。在补丁被提交之前就在评审中表达意见，远比在补丁已提交、你更新仓库、发现你的模拟不再能工作之后再抱怨有效得多。

我们非常重视评审者为维护 gem5 代码质量与一致性所做的努力。不过，评审在维护 gem5 代码质量与对更广泛社区贡献保持开放之间取得平衡也很重要。人们是否愿意贡献（或继续贡献），取决于他们与其他贡献者受到怎样的对待。基于此，以下是对评审者的一些准则：

1.  请记住，提交贡献是一种慷慨行为，对该提交者而言几乎从不是义务。以“感谢你提交这份贡献”之类的话开始评审总是好主意。对新的或偶尔提交的人，一句感谢尤其重要。
2.  总体而言，评审者的态度应是“我们如何把这份贡献好好利用起来”，而不是“提交者必须先解决这项工作里的哪些不足，这份贡献才值得考虑”。
3.  俗话说，“完美是好的敌人”。虽然我们不希望 gem5 退化，但我们也不希望仅仅因为不够最优就绕过有用的功能或改进。如果最优方案不太可能实现，那么接受次优方案可能比没有方案更好。次优方案之后总可以被最优方案取代，也许次优方案还能被逐步改进到那一步。
4.  在要求提交者做额外改动时，请考虑这些改动的成本收益比。特别是，评审者不应因为自己的成本近乎为零就低估所要求改动的成本。要求大范围改动，尤其是向并非长期 gem5 开发者的人提出，可能给只是想通过提交代码来帮忙的人带来沉重负担。如果你作为评审者确实觉得某份补丁需要大范围返工，不妨主动提出自己来做这些改动。
5.  并非每个人都以相同方式使用 gem5，也并非每个人都有相同需求。当某个方案解决的是你没有的问题时，很容易因其缺陷而拒绝它 —— 因为即使最终没有方案你也没有损失。但这对提交补丁的人来说大概不是可接受的结果。换个角度看这一点，它其实是上一条的反面：正如你的成本收益分析不应因为你自己的成本低就低估提交者做出改动的成本，它也不应因为你自己的收益低就低估接受该提交对提交者的收益。
6.  在评论评审请求时要独立、无偏见。不要仅仅因为你或你的组织会从中受益就支持某个补丁，也不要因为你会因此多做工作就反对它。无论你是个人还是在组织中工作的人，都请从社区的角度看待该补丁。
7.  尽量让论证保持技术性、语言保持简单。如果你对某个补丁做出某种主张，请给出依据。

## 决策流程 {#decision-making-process}

关于项目未来的决策通过与社区所有成员（从最新用户到最有经验的 PMC 成员）讨论做出。所有非敏感的项目管理讨论都在 gem5-dev 邮件列表上进行。偶尔敏感讨论会在私有列表上进行。

为确保项目不被无休止的讨论和持续投票拖住，项目实行惰性共识（lazy consensus）政策。这让大多数决策无需诉诸正式投票即可做出。

#### 惰性共识

决策通常涉及以下步骤：

*   提案
*   讨论
*   投票（如果讨论未能达成共识）
*   决策

任何社区成员都可以提出供社区考虑的提案。为就一个新想法发起讨论，他们应在 GitHub discussions 上发帖，或向 GitHub 提交实现该想法的补丁。这会引发对该想法的评审，并在必要时引发讨论。评审与讨论的目标是为该贡献争取批准。由于项目社区中的大多数人都有共同的愿景，往往不太需要讨论就能达成共识。

一般而言，只要没有人明确反对某个提案，就被认为它获得了社区的支持。这称为惰性共识 —— 也就是说，那些没有明确表态的人已隐式同意实施该提案。

惰性共识是项目内非常重要的概念。正是这一过程让一大群人能高效地达成共识，因为对提案无异议的人不必花时间表态，其他人也不必花时间阅读这类邮件。

要让惰性共识有效，必须留出至少两周时间，才能假定对提案没有异议。这一要求确保每个人都有足够时间阅读、消化并回应提案。选择该时间长度是为了尽可能包容所有参与者，不论其所在地与时间安排如何。对于 GitHub 拉取请求，如果两周后仍无评审，提交者应发送提醒。当评审者希望评审某个补丁但需要更多时间时，可以要求补丁提交者推迟提交。如贡献一节所述，每个补丁在提交前应至少获得两个批准。

#### 投票

并非所有决策都能用惰性共识做出。影响项目战略方向或法律地位之类的议题，必须以投票形式获得明确批准。鼓励社区每位成员在所有讨论和投票中表达意见。不过，只有项目维护者和/或 PMC 成员（如上文定义）在决策时拥有有约束力的投票权。关于精英治理模型中投票的单独文档（[http://oss-watch.ac.uk/resources/meritocraticgovernancevoting](http://oss-watch.ac.uk/resources/meritocraticgovernancevoting)）更详细地描述了遵循 Apache 软件基金会所确立实践的这类项目如何投票。
